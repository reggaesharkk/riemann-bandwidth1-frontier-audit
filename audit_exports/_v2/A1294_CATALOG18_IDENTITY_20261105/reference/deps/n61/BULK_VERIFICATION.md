# Reuse and bulk verification assessment

The mathematical assembly architecture is reusable. The same generic cursor-transport theorem handles arbitrary accepted suffix replays at new topology/payload offsets; no extension of its soundness proof was needed for node 61. Upstream split replay and exact-exhaustion soundness compose accepted children. Node61.reused_node63_run imports Node63.replay63 and shifts (0,0) to (2,1). Node61.right_predicate explicitly reuses Node63.source_connected_predicate. The old payload source is not re-elaborated.

There is therefore a credible design for automated chunked proofs without millions of manually authored Lean proofs: a generator supplies exact typed data and complete subtrees, a generic soundness engine checks acceptance, and generic replay/offset lemmas assemble chunks with exact cursor contracts. This is a design assessment, not evidence that the full 13,454,121-node certificate can currently be verified within practical resources.

The present leaf generator still emits many per-segment arithmetic proofs and decoding facts. Terminal 20 needed 132 shared catalog lookup facts and 304 segment-decoding facts to avoid default recursion-depth failures. This is an automatically generated compositional proof, not a demonstrated compact bulk reflection engine. Scaling that literal approach to millions of leaves is not justified. Source-size reduction, object-size reduction and total resource improvement are not established by this audit.

A bulk engine would need bounded typed tables with explicit successful lookup, shared segment/catalog proofs, canonical rational checking, a kernel-checked decoder/source-conversion contract, and a measured acceptance evaluator whose Boolean equality is proved by kernel computation or compositional lemmas. Native evaluation or externally asserted PASS bits would not suffice. Chunk soundness must preserve box geometry, fuel, terminal and quadratic-anchor cursors separately, and complete stream exhaustion. Original-byte/catalog authentication remains external today.

The main unresolved engineering question is acceptance throughput and proof-object growth for heterogeneous complete chunks, including hard leaves, seams, tails and nonzero anchors. These few leaves, mostly constant envelopes, do not establish that range. The large common Mathlib/catalog import footprint and page faults also make timing extrapolation unreliable. No linear full-tree cost forecast is warranted. A small bounded chunk-evaluator benchmark would be the appropriate future experiment, rather than a full-tree build; none was launched here.
